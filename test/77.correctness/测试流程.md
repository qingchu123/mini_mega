# 77.correctness — fp8xfp8 mega kernel 正确性测试流程

> 时间标签 `[261008_15_45]`。实现位于 `test/check.cu`（旧草案里的 `test.cu` 已并入该文件）。
> 运行：`scripts/run.sh check --smoke` / `scripts/run.sh check --all`。

## 1. 目标与场景

- 覆盖 **非 graph（eager）** 与 **graph（含 50-in-1 连跑）** 两种发射方式。
- 主场景：E=256、topk=8、H=6144、I=2048、32 卡；均衡路由（每卡 1..512 token）
  与 TK 实录路由（`test/70.r32_tpr_perf/0928_tk_info.log` 的 744 个 complete launch）。
- 主用例 launch **804900** = MXMOEMega `--routing-fixed-cases 0` 的 case 0
  （该仓库的 256 项逐专家计数已与本工程日志核对逐项一致）。
- 冒烟另含 launch **809200** = MXMOEMega `--routing-fixed-cases 2` 的 case 2
  （实录 skew 14.56x / 40 零专家 / max 233 / 每 rank 收行 17..450），计数同样逐项一致。

## 2. 判据分层

| 层 | 内容 | 通过标准 |
|---|---|---|
| L0 | `launch_prelude` 后 route / publish / task_setup 与 host 模型逐项一致 | 全部 rank 全部字段相等 |
| L1 | rank0 最忙本地专家的 `ffn_hidden` vs CPU 参考（`ref_l1` → E4M3） | rel 7e-2 / abs 2e-3 |
| L2 | `l2_out` 各 N-slice vs CPU 参考（`ref_l2`） | rel 1e-2 / abs 1e-3，每 slice 存在匹配 block |
| REDUCE | 每 rank 的 `y`（全部 token）vs `ref_reduce` | rel 1e-5 / abs 1e-6 |
| graph | 图内 50 个节点的 `y` 与 eager 的 `y` 逐元素比较 | rel ≤ 1e-3 且 finite 位置一致 |

- 路由回放一致性：逐专家计数必须与实录逐字一致（`max|实际-实录| = 0`），构造时即断言。
- 每个 rank 本地判定，`MPI_Allreduce` 汇总；`MPI_MAX` 汇总 rel/误差，`MPI_SUM` 汇总 finite 不一致数。

## 3. 用例集合

- `--smoke`：10 个用例——均衡 16 的 L0+eager / graph×1、实录 case0（`804900`）与
  case2（`809200`，= MXMOEMega `--routing-fixed-cases 2`）各 L0+eager+graph×1 及 graph×50、
  均衡 16/128/24/32 的 graph×50。实测 7.5s，目标 <10s。
- `--all`：9 个均衡 TPR（1,4,16,32,33,64,128,256,512）+ 744 个 TK launch，
  每个用例跑 L0 + eager + graph×50。实测约 4 分钟。

## 4. 实测结果（`check --all`，762 个用例，win = max_tokens）

| 检查 | 结果 |
|---|---|
| L0 | 762/762 PASS |
| L1/L2 | 726/762 PASS，36 例 L1 FAIL |
| REDUCE | 762/762 PASS |
| graph×50 | 762/762 PASS（图与 eager 逐位相同，rel=0） |

未解决：36 例 TK 用例的 L1 不匹配（`max_rel=1.0`，设备值饱和在 E4M3 上界 448）。
同一 launch 在 `--only` 单跑时 PASS，说明与前序用例的状态相关（疑似 pool / 权重槽的跨用例残留），
需进一步定位。均衡路由 9 个 TPR 全部 PASS。

## 5. 过程中的两个真实问题

1. **`bench.cu build_tk_case` 构造出重复专家的非法 top-k。** 它按 `idx/topk` 顺序填 token，
   而 pair 是按专家序排列的，于是同一 token 会拿到多个同一专家（专家 0 有 190 pair
   时其首个 token 全是专家 0）。真实 top-k 不可能重复。该输入下内核 recv 计数出现垃圾值、
   checksum 超时（单次 8~20s）、结果错误。本工程与 MXMOEMega 的录制都是合法的，
   故 `check` 的复现失败不是内核缺陷。`test/mega_common.cuh::routes_from_counts` 已修正。
2. **`bench.cu` 的长尾自适应窗口（win < slot）在 max_tokens=512 时结果错误。**
   `check --all` 用该窗口时 418/762 REDUCE 错、`rel_max ≈ 1/8`（恰为 topk），即每个 token 丢了
   一个专家的贡献；改 `win = max_tokens` 后 762/762 PASS。因此 `mybench`/`check`
   统一取 `win = max_tokens`（`choose_win_cap_counts`）。注意 `test/70`、`test/71` 等既有
   TK 性能数据用的正是自适应窗口，那些数字对应的正确性尚未验证。

## 6. 其它约束与用法

- 超时：`run.sh` 默认 600s（`--all` 3600s）；kernel 内部 spin 上限 `kSpinLimit` 4e6。
- GPU 临界区：`run.sh` 默认持 `.agents/work/lock/lock_gpu`（`GPU_LOCK=0` 关闭）。
- 调试参数：`--only 804300,805600`（只跑指定 launch，仍保留 TPR=512 用例以固定布局）、
  `--graph-nodes N`、`--check-rows N`、`--tk-info F`。
- 冷启动：每进程首个 launch 的跨 rank 同步在冷状态下不可靠（单进程内 32 卡首 launch 约
  16~20s，远超 `kSpinLimit`），故 `check` 在所有检查前先做一次不计入结果的 eager 预热。
