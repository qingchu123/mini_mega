# test/92.r19_l1_bench — r19_l1_big 单 block 隔离扫描与优化

> 目标：把生产 L1 计算函数 `r19_l1_big`（`src/compute_big.cuh:345`）单独拿出来，
> 在单 block（1×512、8 warp）下扫描 M 与模板参数 `(kMT,kPF,kBatch)`，得到纯 L1
> 计算延迟，并据此尝试独立优化。
>
> 口径：K=H=6144、N=2I=4096、block_n=256、nwarps=8、单 block、grid=1；A 走
> fragment；每次采样 5 次预热 + 冲刷 64MB 缓存后 REP=100 次取均值，us/launch。
> 构建/运行：`./build.sh && ./run.sh`（`run.sh` 持 GPU 锁）。基线 `main` @ `6957f7f`。

## 1. 基线扫描（`R19_BPTR=0`，即生产实现）

```
M         2,2,4     2,4,4     2,8,4     3,2,4     3,4,4     4,2,4     4,4,4
16          294*      108       128       135       123       155       184
17          128       115       138       139       129       160       188
24          128       117       142       141       132       162       192
32          129       118       144       142       133       163       193
33          255       228       269       150       142       170       201
40          255       230       272       152       145       173       205
48          255       230       273       153       146       173       206
64          255       234       277       297       278       186       220
```
（`*` M=16 的首格受冷启动影响抖动大，重跑 229~294；其余格两次重跑一致。）

**观察**：
- 最优 `kMT = ceil(M/16)`（M≤32→MT2、33..48→MT3、64→MT4），与生产分派一致。
- 单 block 下时间与数据量**不成正比**：MT2 在 M=17(128) 与 M=32(129) 几乎相同
  → 说明单 block（8 warp/1 SM）是**访存延迟受限**，MMA 被权重装载完全掩盖。
- 由此 `kPF` 是主要杠杆：
  - MT2/MT3：`PF=4` 比 `PF=2` 快 **~9% / ~5%**（M32：118 vs 129；M48：146 vs 153）；
    `PF=8` 反而更慢（寄存器）。
  - MT4：`PF=2` 最优；`PF=4` 变慢（M64：186 → 220）。

## 2. 独立优化：B 基址预计算（`R19_BPTR`）

`r19_load_b16` 每步重算 `((n>>5)*n_tiles+(k>>5))*1024 + lane*16`；改为每个 g0 组
预计算 `b0[q]`，逐步仅 `+1024`。实现在 `src/compute_big.cuh`，宏 `R19_BPTR` 默认 0。

```
M         2,2,4     2,4,4     2,8,4     3,2,4     3,4,4     4,2,4     4,4,4
17          128       111       168       138       122       158       288
32          129       112       174       140       125       161       294
48          255       222       338       151       138       171       306
64          255       223       341       295       265       183       320
```
**观察**：`R19_BPTR=1` 在**中等配置**（MT2/MT3，PF≤4）上再快 ~3~5%
（M32：<2,4,4> 118→112；M48：<3,4,4> 146→138），但**高 PF/MT 配置变差**
（`<4,4,4>` M=64：220→320，寄存器被地址基址占满）。

**单 block 最优** = `kMT=ceil(M/16)`, `kBatch=4`, `kPF=4`(MT2/3)/`2`(MT4), `R19_BPTR=1`：
- M=32：129 → **112µs（−13%）**
- M=48：153 → **138µs（−10%）**

## 3. 端到端验证（`mybench -R 32 -s 1`，交错 2 次）

单 block 的收益**不能迁移到融合核**（32 block / 带宽受限 / 寄存器共享）：

| 配置 | TPR16 | TPR24 | TPR32 | TPR48 | TPR64 | TPR256 |
|---|---:|---:|---:|---:|---:|---:|
| base | 378~415 | 494 | 506 | 547 | 616~646 | 1757~1765 |
| `R19_BPTR=1` | 395~407 | 503~519 | 508~510 | **566~575(+4~5%)** | 640~653 | 1757~1761 |
| `R19_L1_PF=4` | **启动失败**（`error 700`，寄存器溢出） | — | — | — | — | — |

**结论**：
1. 单 block 是**延迟受限**，深预取（PF4）+ 地址预计算（BPTR）可再快 ~10~13%。
2. 但在**融合核**里：`PF=4` 直接把每线程寄存器顶爆导致 **kernel 启动失败**；
   `BPTR=1` 中性偏负（TPR48 +4~5%）。→ 与 `docs/12 §8`、`perf.md:640` 的
   "隔离微基准不能预测真实混合负载"完全一致。
3. 因此若要真正用上单 block 的最优（PF4+BPTR），前提是**把 r19 拆成独立
   kernel 启动**，使其独占寄存器预算；而 L1/L2 拆分在 `perf.md` 已实测净回退，
   需另做取舍。

## 4. 复现

```bash
cd test/92.r19_l1_bench
./build.sh                 # R19_BPTR=0 基线
./run.sh
EXTRA="-DR19_BPTR=1" ./build.sh && ./run.sh   # BPTR 变体
# 端到端（在 src 分支的 worktree）
KERNEL_CFLAGS="-DR19_BPTR=1" scripts/build.sh so mybench
```
