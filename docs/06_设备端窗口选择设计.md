# 06 设备端窗口（win）选择设计

状态：设计草稿（第 3 版，2026-10 更新）。判据未标定，**不得直接实现**，需先完成第 7 节的标定与对照。
第 3 版变更：候选集合改为 {32,48,64,80,96,128}；结构体化（rwk/unk）与 torch 自有分配已完成，见第 11 节。

## 1. 目标

每个 rank 的 kernel 根据本 rank 观察到的全局专家计数 `s_count[e]` 自行选择窗口容量 `win`，
替代 host 侧的 `_select_adaptive_cfg`。目标是实现 auto window（见 docs/07）。

## 2. 前提与已确认的决定

| 项 | 状态 |
|---|---|
| NSLICE 固定为 4（`kNSlice`，编译期） | 已确认 |
| merge 机制去掉，固定 m=1 | 已完成（提交 `ccc861f`，check 三级 PASS） |
| 候选窗口集合 | {32, 48, 64, 80, 96, 128}，全部为 16 的倍数（80/96 已在守卫放行区间内） |
| 守卫放行区间 | `win==slot` 或 `win%16==0 && 32<=win<=slot`（提交 `4ec1272`） |
| 方案 | 编译期实例上界 `cap_hint`，设备端在上界内取值（kCap 实例选择见第 5 节） |
| host 侧 `_select_adaptive_cfg` | 删除（win 不再由 host 计算） |

固定 win 的实测（top50，mybench -s 2，自动 merge 时的数据）：

| win | 均值 (µs) |
|---|---:|
| 32 | 1883 |
| 48 | 1542 |
| 64 | 1289 |
| 128 | 2313 |

最优固定值为 64；选择规则必须至少在 top50 上不劣于固定 64。

## 3. 可用计数（已核实）

- `prefix[e*(R+1)+R] = Σ_r s_recv[r][e]`（`src/prologue.cuh:409-412`），即全局每专家行数。
- compute 入口 `s_count[e] = prefix[e*(R+1)+R]`（`src/compute.cuh:471`）。
- 与 host 旧版 `all_reduce(counts)` 输入相同，所有 rank 得到相同的 `s_count`，因此选出的
  `win` 在 rank 间一致（即使不一致也已证明安全，见 docs/05 第 11 节）。

## 4. 成本模型（待标定）

第 1 版的线性系数 `W64 = 2.66 × W32` 与实测方向相反（实测 64 最快），**不得使用**。

按 docs/07 第 3 节，单 launch 时间近似为

    T(win) ≈ ceil(W(win) · N / G) × t_task(win)
    W(win) = Σ_e ceil(c_e / win),  N = 4,  G = 32

其中 `t_task(win)` 需按实测标定，不是常数。选择规则为

    win = argmin_{win ∈ 候选, 守卫合法} T̂(win)

标定数据来源：按 launch 对候选集合各测一次，记录 `(W(win), 实测耗时)`，拟合 `t_task`。
在标定完成前，不设计具体判据。

## 5. 编译期实例与 cap_hint

- 实例按 `cap_hint` 分派，由 host 按 `slot_capacity` 决定，不由 `win` 决定。
- 设备端选出的 `win` 必须 `<= cap_hint`，否则钳制到 `cap_hint`。
- 候选为 {32, 48, 64, 128} 时，`cap_hint` 的档位需要另行确定（最大候选 128 需要至少一档覆盖）。
- 实例数增加会增加编译时间与代码体积，需评估。

host 侧改动（实现阶段）：
- `launch_config` 不再调用 `_select_adaptive_cfg`，不做 `all_reduce`。
- 返回值只含与负载无关的配置：`cap_hint`、`slot_capacity`、`use_frag`。
- 删除 `_select_adaptive_cfg`、`MXK_ADAPTIVE`、`MXK_ADAPT_EVERY_N`、`_launch_cfg` 缓存。
- `merge_grid` 参数随 merge 机制一并删除（协议层清理，待单独提交）。

## 6. graph 兼容

- `win` 在设备端每次 launch 重新计算，graph replay 时自适应，无需冻结。
- `cap_hint` 与 `slot_capacity` 在 capture 时固定，只决定实例上界。
- replay 时负载超出上界：钳制到 `cap_hint`，结果正确但可能次优。需测试覆盖。

## 7. 待完成的工作（实现前）

1. **标定**：按 launch 对 {32,48,64,128} 测耗时，拟合 `t_task(win)`，验证 `T̂` 的排序是否与实测一致。
2. **选择规则**：基于标定模型给出判据；判据必须可在 kernel 内以 EPR 个元素的廉价运算完成。
3. **对照**：设备端判据输出 vs 逐 launch 实测最优，统计选择偏差与损失。
4. **守卫**：设备端不能 `exit(2)`。守卫仍在 host；设备端通过钳制保证取值合法。
5. **kRing 与显存**：当前 kRing=16（每 rank 约 1 GiB）。候选 128 的窗口数减少，但每槽容量需覆盖 `slot_capacity`，需确认。

## 8. 风险

1. 标定样本不足时，选择规则可能过拟合 top50。需要独立的负载集合验证。
2. 逐 launch 最优的收益未知；若小于固定 64 的收益，选择的复杂度不值得。
3. `cap_hint` 上界若设得过保守，会压低设备端选择空间。
4. 每 rank 独立选 win 已证明安全，但 `cap_hint` 必须全局一致（由 `slot_capacity` 决定，各 rank 相同）。

## 9. 验证计划（实现阶段）

1. 判据单元测试：同一 `s_count` 输入，host 对照实现与设备端输出一致。
2. check smoke 5/5、子集 12/12、top50 52/52。
3. 选择结果 vs 固定 win=64：top50 与独立负载集合上的 `mybench -s 2 -top 50` 对比。
4. graph 与 eager 一致性（check 已覆盖）。
5. check 单次耗时 ≤ 10 s（top50 目前 13–18 s，需拆分，见 perf 记录）。

## 10. 待确认

1. 候选集合是否包含 32（守卫已放行，但固定 32 性能最差，仅在标定中证明其有用时保留）。
2. `cap_hint` 的档位数与取值（建议先按 128 单档）。
3. 标定数据集：使用 top50 之外的独立负载，避免过拟合。

### 11.1 torch 路径的已知问题与修复

- 现象：单卡建档预热时 `mega_kernel<...,0>` 报 ATU/Xnack 非法访存。
- 根因：C++ 自有分配后，设备表 `d_base_ptrs`/`d_unk_ptrs` 只分配未写入，kernel 经 `unk_peers[rank]` 读到随机地址。
- 修复：`create_symm_buffer_owned` 建档时写入 self 项；远端项由 `symm_import_peers` 填充。
