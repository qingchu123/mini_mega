# 12 L1 函数族：参数模板 / 资源占用 / 适用场景

> 目的：逐条说明 megakernel 里各 L1 GEMM 变体的模板参数、寄存器/smem 占用、预取深度
> 与理论适用场景；配套测试见 `test/80.l1_func_bench/`（单独跑每个函数）。
> 口径：H=6144、I=2048、topk=8、EPR=8、block_n=256、kNSlice=4、kComputeWarps=8、
> kNTilesPerWarp(kNT)=2、kM=16。
> 对齐提交：`37accdc`（`[261011_0200] build: kernel 实例拆分到 src/multi_compile/*.cu`）。

## 1. 共同约定

- GEMM：`M=count`（窗口行数）× `N=2I=4096`（L1） × `K=H=6144`；MMA=`16(M)x16(N)x32(K)`。
- tiling：M 按 16（kM）、N 按 16（MMA）/`block_n=256`（组）、K 按 32（kKStep）。
- `MT`=同时处理的 M-tile 数（权重跨 M 复用）；`kBatch`=一次 K 迭代共享 A 的 N 组数；
  `kPrefetch(PF)`/`kBPF`=K 循环预取深度（2 的幂，ring 用 `& (PF-1)` 索引）。
- `acc = Fp8Accumulator[kBatch][MT][kNT]` → **寄存器** `= kBatch*MT*kNT*4` floats。
- `kNT=kNTilesPerWarp=2` 恒成立（layout16b 配对装载要求 `kNTiles==2`）。
- A 来源：行主序 pool、fragment（`fbase`/`f2`），或 r24 的 **A-smem**（由 F 异步搬入）；
  B 来源：global 权重（`ldg` 16B/lane 寄存器预取）。
- 分派几何：`g_l1=(2I/block_n)/nslice_eff`（NS=4→4、NS=8→2）；
  `g_l2=(H/block_n)/nslice_eff`（NS=4→6、NS=8→3）。

## 3. 各函数详解

### 3.1 `l1_gemm_swiglu_body_paired`（遗留 / 微基准）

- **机制**：K 循环按 `kBatch` 个 N 组（gate/up 配对，kBatch 偶数）共享一份 A（`a_pipe`），
  A/B 走**寄存器预取环**（`a_pipe[kPrefetch][kMTiles]`、`b_pair[kPrefetch][kBatch]`）。
  `kUseFrag=true` 时 A 从 fragment（4-line 连续）读，否则行主序 pool（16-line 散射）。
- **现状**：生产分派（`dispatch_pull_body` → `r19_small_task`/`r19_big_task`）**已不再调用**
  该函数；仅 `test/79.l1_gemm_best`、`test/80.l1_func_bench` 隔离微基准使用。
  历史实例：`<2,2,1,4>`/`<2,2,2,4>`（MT1/MT2）、`<2,2,3,4>`（MT3），见 test/80。
- **寄存器**：`<PF,2,MT,4>` → `4*MT*2*4 = 32*MT` floats（MT2→64、MT3→96）。
- **smem**：0（B 只在寄存器）。

### 3.2 `r19_l1_big`

- **机制**：外层 `c0` 按 `kMT*kM`(=kMT*16) 行分组；组内 K 循环外层、M-tile 内层，
  B fragment 在 `kMT` 个 M-tile 间共享（B 每组只读一遍 → 权重遍数
  `= ceil(count/(kMT*16))`）。A 走 `R21_LDA`：`fbase` 非空读 fragment（4 line/指令），
  否则行主序 pool（16 line）。尾组不足由 `r19_load_a` 零填充、写回按 `row<cc` 跳过。
  组对余数（恒偶数）递归 `<kMT,kPF,2>` 收尾。
- **寄存器**：`kBatch*kMT*kNT*4 = 32*kBatch*MT` floats；`<4,2,4>` → 128、
  `<3,2,4>` → 96、`<3,2,2>` → 48、`<1,2,4>` → 32。
- **smem**：0（A/B 都过寄存器）。
- **生产实例**：`<1,2,4>`/`<1,2,2>`（≤16）、`<4,2,4>`/`<4,2,2>`（17..32）、
  `<3,2,4>`/`<3,2,2>`（33..48）、兜底 `<4,2,4>`。
- **场景**：小/中档、无 fragment 或非 async 几何的大档回退。

### 3.3 `r24_l1_big`

- **机制**：A 走 **A-smem 双缓冲**（异步 `__builtin_mxc_ldg_b128_bsm`）；B 走直装
  （`ldg` 16B/lane，预取环 `kBPF`）；每个 stage = `kKS` 个 K step × `kMT` 个 M-tile，
  smem 布局 `[j][m][row][32B]` 与 F_A 逐字一致，LDS 直读 native fragment。
  行区间 `[c0_begin, c0_end)` 分段：整块 `kMask=false` 无掩码快路径 + 尾块
  `kMask=true`（越界 tile 折叠到最后一 tile + `row<cc` 掩码写/checksum）；
  `kMTAct`=尾块活跃 M-tile 数（编译期裁剪 A 搬运/MMA/epilogue）。
- **smem**：`kBufBytes=kMT*kKS*512`，双缓冲 `2*kBufBytes`。生产 `R24_MT=8`、`R24_KS=8`
  → `2*8*8*512 = 64KB`，与 `b_smem` 以 union 折叠（kernel 作用域 `a_smem`）。
- **寄存器**：`kBatch*kMT*kNT*4`；`<8,8,2>` → **128 floats**（顶格）。
- **生产实例**：`<3,16,4,true,3,BPF>`（33..48）、`<4,R24_KS,2,false,4,BPF>`（64）、
  `<8,R24_KS,2,false,8,BPF>`（>64 全块）、尾块 `<1,16,2,true,1,BPF>` /
  `<8,R24_KS,2,true,5,BPF>` / `<8,R24_KS,2,true,8,BPF>`。
- **场景**：有 `fbase` 的中/大档；MT8 把权重遍数减半；A-smem 双缓冲隐藏 A 延迟。

## 4. 任务层分派（谁调用这些 L1）

- `dispatch_pull_body` (compute.cuh:696) 按 `count` 分派：
  - `count <= kM`(16) → `r19_small_task` (compute_big.cuh:1688)；
  - `count >  kM`      → `r19_big_task`   (compute_big.cuh:1327)。
- 两者均 `__noinline__`（`R19_SMALL_ATTR`/`R19_BIG_ATTR`），独立寄存器/栈分配，互不污染。
- `[R31] kSmallOnly=true` 实例只编小任务体（大任务体不实例化），供 `win_cap<=kM` 场景。
- `[L1L2-SPLIT] kPhase`（`Both`/`L1`/`L2`）里非本节相位由 `if constexpr` 编译期消除
  （`CM_L1L2_SPLIT` 默认 0，即 Both）。
- `r24` 系的 B 预取深度 `BPF = kR24BPF = (kCap>0) ? 4 : R24_BPF`：tk/长尾实例
  （`megakernel` 的 `kCap=48/64` 变体，见 `src/multi_compile/kernel_cap48.cu`、
  `kernel_cap64.cu`）用 4，均衡大档保持 2。

## 5. count 档 → 函数映射

**`r19_small_task`（count≤16，按 `g_l1`）**

| g_l1 | L1 |
|---|---|
| 4（NS=4） | `r19_l1_big<1,2,4>` |
| 2（NS=8） | `r19_l1_big<1,2,2>` |

**`r19_big_task`（count>16，compute_big.cuh:1392-1504）**

| count | 条件 | L1 路径 |
|---|---|---|
| 17..32 | `g_l1%4==0` | `r19_l1_big<4,2,4>` |
| 17..32 | `g_l1=2`（NS=8） | `r19_l1_big<4,2,2>` |
| 33..48 | `g_l1%4==0` 且 `fbase` 且 `(k_in/32)%16==0` | `r24_l1_big<3,16,CM_L1_BATCH,true,3,BPF>` |
| 33..48 | 同上但无 `fbase`/几何不符 | `r19_l1_big<3,2,4>` |
| 33..48 | `g_l1=2`（NS=8） | `r19_l1_big<3,2,2>` |
| =64（49..64 且 `count%64==0`） | `fbase` 且 `(k_in/32)%R24_KS==0` | `r24_l1_big<4,R24_KS,2,false,4,BPF>` |
| >64 | `kAsync`：`fbase` 且 `count>64` 且 `(k_in/32)%R24_KS==0` 且 `g_l1%2==0` | 全块 `r24_l1_big<8,R24_KS,2,false,8,BPF>` |
| >64 尾块 | `count-full<=16` 且 `(k_in/32)%16==0` | `r24_l1_big<1,16,2,true,1,BPF>` |
| >64 尾块 | 活跃 tile 数==5 | `r24_l1_big<8,R24_KS,2,true,5,BPF>` |
| >64 尾块 | 其他 | `r24_l1_big<8,R24_KS,2,true,8,BPF>` |
| 兜底 | 非 async 几何 | `r19_l1_big<4,2,4>` |
| 兜底 | `kCap=48` 实例（`win_cap<=48`） | `r19_l1_big<3,2,4>` |
| 兜底 | `kCap=64` 实例（`win_cap<=64`） | `r19_l1_big<4,2,4>` |

> `kAsync` 成立要求 `(k_in/32)%R24_KS==0`（H=6144 → 192，R24_KS=8 整除）。
> `>64` 时若 `full==count`（128 整除）只跑全块；否则「全块 + 尾块」两段式。

## 6. 理论取舍（为什么这么多）

| 维度 | 小 M（≤16） | 中 M（17..48） | 大 M（>64） |
|---|---|---|---|
| 权重复用 | 不划算（MT1） | MT3/MT4 | MT8 |
| A 装载 | 行主序即可 | fragment 更优 | A-smem 双缓冲（bsm 异步） |
| 寄存器 | 低（acc≤32） | 中（≤128） | 高（128，顶格） |
| 同步/流水 | 简单 | 单批 N | async 两段式 + 尾块掩码 |

- 大 MT/大 kBatch → 权重省、acc 宽、寄存器压力大 → 只在"能摊薄"的大 M 启用。
- 小 M → acc 小、寄存器省，但权重不复用 → 走小档。
- `kCap` 编译期裁掉不可达档（win_cap≤48/64 时不实例化 MT8 异步档，见 §4）。
- 隔离微基准（固定 M）**不能**预测真实混合负载最优变体，选型须端到端 A/B（见 §8）。

## 7. 实测（test/80.l1_func_bench，真实 body 按分派逐 M，us/launch，grid=32/block=512）

| M | 变体 | frag | 行主序 |
|---:|---|---:|---:|
| 16 | `paired<1>` | 250* | 359* |
| 17 | `paired<2>` | 103.5 | 118.3 |
| 32 | `paired<2>` | 106.2 | 153.9 |
| 33 | `r24<3,16>` | 139.4 | 162.3 |
| 48 | `r24<3,16>` | 141.8 | 205.2 |
| 64 | `r24<4,8>` | 172.8 | 308.8 |
| 65 | `r24<8,8>` | 345.4 | 560.5 |
| 96 | `r24<8,8>` | 345.5 | 573.2 |
| 128 | `r24<8,8>` | 345.4 | 586.6 |

（*M=16 为首测冷启动，偏高。表中 17/32 档为历史 `paired` 实例，生产现已改用
`r19_l1_big<4,...>`；本表保留用于 frag vs 行主序与档位跳变对照。）

**结论**：
1. **fragment（frag）恒优于行主序**：−40~44%（如 M=64：172.8 vs 308.8；M=128：345 vs 587）。
   印证 A 走 4-line fragment 的收益（也说明"fbase 恒取 frag"的方向对）。
2. **存在 64→65 的大跳变**（`r24<4,8>` 172.8 → `r24<8,8>` 345.4，≈2×）——即
   `count>64` 进入 async/MT8 路径的台阶（与 docs/11 标定的 `t_task` 跳变一致）。
3. M=17..32 用 `paired<2>`：103~106（frag），M 增大但每档只多付整 tile。

## 8. 交叉扫描与端到端否决（重要教训）

- **隔离扫描**（test/80 的 `r24_full`，循环 c0 覆盖整 M，32 block 同任务）：
  `r24<4,8,4>`（M=65..128 约 310µs）看似优于 `r24<8,8,2>`（约 326µs）。
- **端到端验证**：把 `kAsync` 改为 MT4/B4（caller 循环 c0）后，`win=128` balanced
  TPR256 = **1796 → 1926µs（+7%，更差）**，TPR64 持平。→ **已回退**（`src/compute_big.cuh`
  恢复 MT8/B2）。
- **结论**：**隔离微基准（固定 M、所有 block 做同一任务）不能预测真实混合负载的最优
  L1 变体**（真实是 32 block 各做不同 (expert,window)、寄存器/occupancy/访存相互影响）。
  L1 变体选择必须**端到端** A/B 验证，不能只靠隔离扫描。
- 保留现状：`count>64` 用 `r24<8,8,2>`（MT8/B2）。

## 9. MT16（kBatch=1 两遍）隔离实测否决

- **动机**：MT8 的 `acc = kBatch*MT*kNT*4 = 128` 已顶格；MT16 只能靠 `kBatch=1`（acc=128），
  但 SwiGLU 需 gate/up 配对 → 需重构为「gate/up 各跑一次 K 循环、gate 暂存 smem」。
- **实测**（`test/80`，A 走 smem、K=6144、grid=32、50 次中位，us/launch）：

  | M | `r24<8,8>`（现役） | MT16 kBatch=1 两遍 | 比 |
  |---:|---:|---:|---:|
  | 64 | 241 | 544 | 2.30× |
  | 128 | 345 | 545 | 1.58× |
  | 256 | 668 | 1156 | 1.73× |
  | 384 | 990 | 2249 | 2.27× |
  | 512 | 1313 | 2255 | 1.72× |

- **端到端旁证**（均衡场景 R=32）：朴素把 `R19_L1_MT` 设 16 需 `R24_KS=4`（否则 smem
  131104 > 131072 启动失败），且 `MT16/KS4` 全面回退：win=128 TPR128 1013→4804µs、
  TPR256 1894→4875µs；win=512 TPR512 3685→9583µs。
- **根因**：**A-smem 搬运翻倍**。`r24<8,8,2>` 每趟 K 循环搬 8 tile 供 2 组（gate/up）共享；
  MT16/kBatch=1 每趟搬 16 tile 却只服务 1 组 → 覆盖同样 (16 tile×2 组) 需 **2 趟 = 2× A 流量**，
  外加 2× stage 同步 + gate 的 smem 往返。B 复用翻倍救不回。
- **旁证**：MT8 下单独把 `R24_KS` 8→4（stage/同步翻倍）实测中性（±3%）→「2× 同步」本身非主因，
  **A 流量才是**。
- **结论**：**MT16 经 kBatch=1 重构是净回退，放弃**。在 kBatch=2 约束下 MT=8 仍是 L1 大档最优（acc 顶格 128）。
