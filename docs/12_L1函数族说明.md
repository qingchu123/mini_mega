# 12 L1 函数族：参数模板 / 资源占用 / 适用场景

> 目的：逐条说明 megakernel 里各 L1 GEMM 变体的模板参数、寄存器/smem 占用、预取深度
> 与理论适用场景；配套测试见 `test/80.l1_func_bench/`（单独跑每个函数）。
> 口径：H=6144、I=2048、topk=8、EPR=8、block_n=256、kNSlice=4、kComputeWarps=8、
> kNTilesPerWarp(kNT)=2、kM=16。

## 1. 共同约定

- GEMM：`M=count`（窗口行数）× `N=2I=4096`（L1） × `K=H=6144`；MMA=`16(M)x16(N)x32(K)`。
- tiling：M 按 16（kM）、N 按 16（MMA）/`block_n=256`（组）、K 按 32（kKStep）。
- `MT`=同时处理的 M-tile 数（权重跨 M 复用）；`kBatch`=一次 K 迭代共享 A 的 N 组数；
  `kPrefetch(PF)`=K 循环预取深度。
- `acc = Fp8Accumulator[kBatch][MT][kNT]` → **寄存器** `= kBatch*MT*kNT*4` floats。
- A 来源：行主序 pool，或 fragment（`fbase`）；B 来源：global 权重（寄存器预取）或 smem 异步。

## 2. L1 函数一览

| 函数（定义） | 模板参 | acc 寄存器(floats) | smem | B 通路 | 适用 count |
|---|---|---|---|---|---|
| `l1_gemm_swiglu_body_paired` (compute.cuh:259) | `<kPrefetch, kNTiles, kMTiles, kBatch, kUseFrag>` | `kBatch*MT*kNT*4` | 0 | 寄存器预取 PF | ≤48（小/中档） |
| `l1_gemm_swiglu_body_bsm` (compute.cuh:480) | `<kMTiles, kBatch, kBR>` | `kBatch*MT*kNT*4` | `kBR*kBatch*8*1024` | **smem 异步** | 实验档（默认关） |
| `r19_l1_big` (compute_big.cuh:350) | `<kMT, kPF, kBatch>` | `kBatch*MT*kNT*4` | 0 | 寄存器预取 PF | 兜底（非 async 大档） |
| `r24_l1_big` (compute_big.cuh:568) | `<kMT, kKS, kBatch, kMask, kMTAct, kBPF>` | `kBatch*MT*kNT*4` | A-smem（union 64KB） | **A-smem 双缓冲 + B async** | >48（大档） |

> `R24_KS=8`、`R24_BPF=2`、`CM_L1_PF=2`、`CM_L1_BATCH=4`、`R19_L1_MT=8`、`R19_L1_PF=2`、`R19_L1_BATCH=2`。

## 3. 各函数详解

### 3.1 `l1_gemm_swiglu_body_paired`
- **机制**：K 循环按 `kBatch` 个 N 组（gate/up 配对，kBatch 偶数）共享一份 A（`a_pipe`），
  A/B 走**寄存器预取环**（`a_pipe[kPrefetch][kMTiles]`、`b_pair[kPrefetch][kBatch]`）。
  `kUseFrag=true` 时 A 从 fragment（4-line 连续）读，否则行主序 pool（16-line 散射）。
- **实例**（r19_small/big_task 里）：
  - `paired<2, 2, 1, 4>` / `paired<4, 2, 1, 2>`（count≤16，MT1）
  - `paired<2, 2, 2, 4>` / `paired<2, 2, 2, 2>`（17..32，MT2）
  - `paired<2, 2, 3, 4>` / `paired<2, 2, 3, 2>`（33..48 回退，MT3）
- **寄存器**：B4/MT2/NT2 → 64；B4/MT3/NT2 → 96 floats。
- **smem**：0（B 只在寄存器）。
- **PF**：默认 2（藏 global 装载延迟；见 test/78：PF2 相对 PF1 −20%）。
- **场景**：中小 M、A 行主序/fragment 均可、B 权重复用适中。

### 3.2 `l1_gemm_swiglu_body_bsm`
- **机制**：B 先异步搬到 **smem**（`__builtin_mxc_arrive` 分级流水），MMA 时 LDS 读。
  消除寄存器预取深度限制（在飞 B = kBR*kBatch）。
- **smem**：`kBR*kBatch*8*1024` 字节。
- **场景**：B 装载带宽/延迟受限、想加深 B 流水时；**默认关**（`CM_USE_BSM=0`，
  实测 tk 中性/略负）。

### 3.3 `r19_l1_big`
- **机制**：外层按 `kMT` 个 M-tile 分组、组内 B 在 M-tile 间共享（B 只读一遍/组），
  B 走寄存器预取（同 paired 的 M 档版）。非 async 固定 `MT4/B4` 回退。
- **寄存器**：`r19_l1_big<4,2,4>` → 4×4×2×4 = 128 floats（顶格一半）。
- **场景**：count>48 但 `kAsync` 不成立（如 win_cap 非 16 整除、无 fragment）的兜底。

### 3.4 `r24_l1_big`
- **机制**：A 走 **A-smem 双缓冲**（异步搬 A），B 走 **async（bsm）**；`kMT` 个 M-tile
  共享 B；`kMask`=尾块掩码（`kMTAct` 活跃 tile 数，`kBPF`=B 预取深度）。
  行区间 `[c0_begin, c0_end)` 两段式（整块无掩码 + 尾块掩码）。
- **smem**：A-smem 用 union（`2*R24_MT*R24_KS*512` = 64KB），与 b_smem 折叠互斥。
- **寄存器**：`r24_l1_big<8,8,2,...>` → 2×8×2×4 = **128 floats**（MT8 权重读减半的代价）。
- **实例**：`<3,16,B,true,3>`（33..48）、`<4,8,B2,false,4>`（49..64）、`<8,8,2,false,8>`（>64）。
- **场景**：大 M（>48），尤其 count>64 的 async 快路径；MT8 把权重读遍数减半。

## 4. count 档 → 函数映射（r19_big_task）

| count | L1 路径 |
|---|---|
| ≤16 | `r19_small_task` → `paired<2,2,1,4>` / `paired<4,2,1,2>` |
| 17..32 | `paired<2,2,2,4>` / `paired<2,2,2,2>` |
| 33..48 | `r24_l1_big<3,16,B,true,3>`（有 fbase）否则 `paired<2,2,3,4>` |
| 49..64 | `r24_l1_big<4,8,B2,false,4>`（有 fbase 且整除） |
| >64 | `r24_l1_big<8,8,2,false,8>` + 尾块 |
| 兜底 | `r19_l1_big<4,2,4>` |

## 5. 理论取舍（为什么这么多）

| 维度 | 小 M（≤16） | 中 M（17..48） | 大 M（>48） |
|---|---|---|---|
| 权重复用 | 不划算（MT1） | MT2/MT3 | MT4/MT8 |
| A 装载 | 行主序即可 | fragment 更优 | A-smem 双缓冲 |
| 寄存器 | 低（acc≤64） | 中（≤96） | 高（128，顶格） |
| 同步/流水 | 简单 | 单批 N | async 两段式 + 尾块掩码 |

- 大 MT/大 kBatch → 权重省、acc 宽、寄存器压力大 → 只在"能摊薄"的大 M 启用。
- 小 M → acc 小、寄存器省，但权重不复用 → 走小档。
- `kCap` 编译期裁掉不可达档（win_cap≤48 时不实例化 MT8）。

## 6. 实测（test/80.l1_func_bench，真实 body 按分派逐 M，us/launch，grid=32/block=512）

| M | 变体 | frag | 行主序 |
|---:|---|---:|---:|
| 16 | `paired<1>` | 250* | 359* |
| 17 | `paired<2>` | 103.5 | 118.3 |
| 32 | `paired<2>` | 106.2 | 153.9 |
| 33 | `r24<3,16>` | 139.4 | 162.3 |
| 48 | `r24<3,16>` | 141.8 | 205.2 |
| 64 | `r24<4,8>` | 172.8 | 308.8 |
| 65 | `r24<8,8>` | 345.4 | 560.5 |
| 96 | `r24<8,8>` | 345.5 | 573.2 |
| 128 | `r24<8,8>` | 345.4 | 586.6 |

（*M=16 为首测冷启动，偏高。）

**结论**：
1. **fragment（frag）恒优于行主序**：−40~44%（如 M=64：172.8 vs 308.8；M=128：345 vs 587）。
   印证 A 走 4-line fragment 的收益（也说明"fbase 恒取 frag"的方向对）。
2. **存在 64→65 的大跳变**（`r24<4,8>` 172.8 → `r24<8,8>` 345.4，≈2×）——即
   `count>64` 进入 async/MT8 路径的台阶（与 docs/11 标定的 `t_task` 跳变一致）。
   → **待查**：count∈(64,128] 是否 `r24<4,8>`（非 async）比 `r24<8,8>` 更快？若更快，
   当前分派在 65..128 档是次优。
3. M=17..32 用 `paired<2>`：103~106（frag），M 增大但每档只多付整 tile。

**下一步**：交叉扫描（同一 M 试多个变体）定位 65..128 档的最优变体；把 frag/row-major、
PF、batch 的敏感度也纳入。

## 7. 交叉扫描与端到端否决（重要教训）

- **隔离扫描**（test/80 的 `r24_full`，循环 c0 覆盖整 M，32 block 同任务）：
  `r24<4,8,4>`（M=65..128 约 310µs）看似优于 `r24<8,8,2>`（约 326µs）。
- **端到端验证**：把 `kAsync` 改为 MT4/B4（caller 循环 c0）后，`win=128` balanced
  TPR256 = **1796 → 1926µs（+7%，更差）**，TPR64 持平。→ **已回退**（`src/compute_big.cuh`
  恢复 MT8/B2）。
- **结论**：**隔离微基准（固定 M、所有 block 做同一任务）不能预测真实混合负载的最优
  L1 变体**（真实是 32 block 各做不同 (expert,window)、寄存器/occupancy/访存相互影响）。
  L1 变体选择必须**端到端** A/B 验证，不能只靠隔离扫描。
- 保留现状：`count>64` 用 `r24<8,8,2>`（MT8/B2）。
