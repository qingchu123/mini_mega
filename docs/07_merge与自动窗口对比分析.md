# 07 merge 机制与 kernel auto window 机制对比分析（理论）

> 状态：纯理论分析，未做新的实测。文中引用的数字仅为既有测量（perf.md 与本轮 top50 记录），用于校验模型方向，不作为新结论。

## 1. 范围与符号

| 符号 | 含义 |
|---|---|
| G | grid 大小（block 数），当前为 32 |
| N | kNSlice，当前固定为 4 |
| E | 本 rank 本地专家数（EPR，当前为 8） |
| c_e | 专家 e 接收的行数（(token, expert) 对数） |
| w | 窗口容量（win） |
| W_e | 专家 e 的窗口数 = ceil(c_e / w) |
| W | Σ_e W_e，全部窗口数 |
| m | merge，2 的幂且整除 N |
| T | 逻辑任务数 = W × N |
| T_phys | 物理任务数 = T / m |

## 2. 两种机制的定义

**merge（任务粗化）**
- 同一窗口内相邻的 m 个逻辑 slice 合并为一个物理任务。
- 不改变窗口数 W，不改变窗口大小 w。
- 由 `raw_tasks / merge ≤ merge_cap` 决定，merge_cap 缺省为 G。
- 运行期变量：`nslice_eff = N / m`。

**auto window（窗口容量选择）**
- 为每次 launch 选择窗口容量 w（候选 32/48/64/128 等）。
- 改变 W_e = ceil(c_e / w)，从而改变 W 与 T。
- 窗口内 N 个 slice 保持不变，`nslice_eff` 恒为 N。

两者的作用对象不同：merge 作用于"窗口内的 slice 分组"，auto window 作用于"窗口的切分粒度"。

## 3. 统一代价模型（定性）

设一个物理任务的耗时为

    t_task(m, w) ≈ t_fix + m · t_slice(w)

其中：
- t_fix：每个任务固定开销（取任务、标记、同步等）。
- t_slice(w)：处理一个逻辑 slice 的工作量，包含 A（激活）读取、权重列段读取、计算与写出。

整个 launch 的时间近似为

    T_launch ≈ ceil(T_phys / G) × t_task(m, w)
             = ceil(W·N / (m·G)) × (t_fix + m·t_slice(w))

由此可见两个因素的作用方式：
- 波数项 ceil(W·N/(m·G)) 随 m 减小（粗化）而减小，随 W 增大而增大。
- 每波单任务时间随 m 线性增长。

若忽略离散化（ceil），merge 对 m·波数 的乘积是抵消的，只留下 t_fix 与 A 读取的节省。

此外，权重读取总量为 **W × 专家权重大小**（每个窗口都要读取所属专家的权重列段），与 m 无关，但与 W 成正比。

## 4. merge 机制分析

### 4.1 收益
- **A 读取节省**：一个物理任务内 m 个 slice 共享同一窗口的 A 行，A 读取次数约减少为 1/m。
- **t_fix 摊销**：任务级固定开销（取任务、标记写入、wait）按物理任务数摊销。
- **波数减少**：物理任务数降为 1/m，在 T 很大时可减少单波数量。

### 4.2 代价与局限
- **波数抵消**：单任务时间约增加 m 倍，波数约减少 m 倍，两者相乘后主项基本抵消。收益只剩 A 读取与 t_fix 的部分。
- **不改变权重流量**：权重读取量 ∝ W，merge 不影响。
- **不改变负载分布**：merge 只看 raw_tasks 总量，对所有专家统一使用同一个 m，无法针对"大专家 / 小专家"区别对待。
- **粒度变粗**：m 增大时，单任务占用 block 的时间变长，在 T_phys 接近或小于 G 时，部分 block 空转。
- **协议复杂度**：nslice_eff 成为运行期变量，combine 标记、REDUCE 等待、slice_flags 写法都要按 m 处理。perf.md 记录过 merge=1 多波协议的陈旧读与 kNSlice=16 数值错误，说明这部分是高风险区域。

### 4.3 对 NSLICE=4 的特殊性
- m=4 时 nslice_eff=1，一个物理任务即一个完整 (e, w)。
- m=2 时 nslice_eff=2，一个物理任务覆盖窗口内一半列段。
- 对 N=4 而言，m 的取值只有 1/2/4 三种，可调的自由度很小，难以精细控制代价。

## 5. auto window 机制分析

### 5.1 收益
- **直接控制 W**：w 越大，W 越小，权重读取总量越少。
- **按专家形状选择**：不同 launch 的 c_e 分布不同，w 可以逐 launch 调整，避免固定一个 w 的全局折中。
- **与 merge 解耦**：N 固定，协议中 `nslice_eff` 恒定，减少运行期分支。

### 5.2 代价与局限
- **权重流量 ∝ W**：w 小则 W 大，权重读取增加。这是 w 过小的主要代价。
- **负载均衡与任务数**：w 大则 T 小。当 T 远小于 G·（一波的并行度）时，block 空转，单任务串行时间变长。这是 w 过大的主要代价。
- **离散选择**：w 取离散候选，每个 launch 的 c_e 分布导致 W 的台阶效应，需要选择规则。
- **守卫与容量**：slot 容量与 win 的关系需要保证，目前守卫只放行 win==slot 或 16 的倍数且 32≤win≤slot。
- **选择代价**：设备端选择需要的判据（如 max_expert、中位数）必须可在 kernel 内廉价计算，并与 host 侧保持一致。

### 5.3 既有测量与模型方向的一致性（引用，不新测）
固定 win、自动 merge、top50 均值（既有记录）：

| win | 均值 (µs) | 定性解释 |
|---|---:|---|
| 32 | 1883 | W 大，权重流量高 |
| 48 | 1542 | |
| 64 | 1289 | 本轮固定 win 中最优 |
| 128 | 2313 | T 小，负载不均衡 |

该曲线呈 U 形，与 5.2 的两端代价一致。这说明 auto window 的搜索空间是有意义的，但其最优点依赖负载分布。

另外，此前基于"64 每波成本 2.66 倍于 32"的系数估计与上述方向相反，说明简单的线性成本系数不可用，需要标定或使用更合理的模型。

## 6. 对比总结

| 维度 | merge | auto window |
|---|---|---|
| 作用对象 | slice 分组 | 窗口粒度 |
| 改变 W | 否 | 是 |
| 改变权重流量 | 否 | 是（∝ W） |
| 改变 A 读取 | 是（÷m） | 是（随 W 变化） |
| 改变波数 | 是（÷m） | 是（随 T 变化） |
| 感知专家形状 | 否（全局统一 m） | 是（逐专家 c_e，可逐 launch 选择） |
| 对协议的影响 | 大（nslice_eff 运行期变化，标记与等待受影响） | 小（N 固定，协议不变） |
| 主要风险 | merge=1 多波正确性、粗化损失并行度 | 选择规则、守卫、slot 容量 |
| 理论收益上限 | 有限（主项抵消） | 较大（同时作用于权重流量与负载） |

## 7. 结论（理论层面）

1. **auto window 在理论上更有潜力**。它同时作用于权重流量（∝ W）与负载均衡（T 与 G 的关系），而 merge 的主要收益项在波数与单任务时间之间相互抵消。
2. **merge 的增量价值较小**。在 N=4 下，m 的可调范围仅 {1,2,4}，且 merge 无法区分专家形状。在 auto window 生效后，merge 的边际收益预计更小。
3. **建议的方向**：固定 N=4，去掉 merge（即 m=1），以 auto window 作为主要调节手段。这同时简化协议（nslice_eff 恒定）。
4. **前提条件**：去掉 merge 后，T 可能超过 G 形成多波。m=1 在 N=4 下的数值正确性需要用 check 验证，这是进入实施前必须完成的事项。
